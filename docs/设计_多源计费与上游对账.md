# 设计评审稿：多源计费口径变更 + 上游按源对账

状态：**已实现**（本文保留为设计背景与决策记录；落地形态见下方「实现差异」与 `docs/DESIGN.md`）
适用范围：全部路由（swfp 五源聚合为主要驱动场景，单源路由同步纳入统一结构）

---

## 0. 实现差异（以代码为准）

实现时并入了「按维度串行寻源 + 按实得内容计费」这一更大的变更，故与本文原始设计有四处出入：

| 本文原设计 | 实际落地 |
|---|---|
| 保留并发聚合器 `Aggregator`，只交换两个 switch 分支 | `Aggregator` 被 `Sourcer`（串行、命中即停、逐源去重）取代；`aggregate.go` 只留 `aggSection`/`classify` 等共享辅助 |
| `SourceCall` 只有三态 `ok/empty/error` | 增加第四态 `skipped`（被更高优先级源短路 / 本次已调过 / 超时延预算），未调用的源同样出轨迹行 |
| 计费仍是「有查得就按单价计一次」 | 改为按**实得维度**三档定档（`both`/`invoice`/`tax`，皆无不计费），费率挂 license + 全局缺省兜底，并落 `amount_fen` 与 `upstream_cost_fen` |
| 迁移文件 `0005_upstream_call.sql`，含 legacy 回填（D4） | 迁移为 `0007_sourcing_billing.sql`（建表 + 台账/审计/license 新列）；`upstream_call` 另有 `seq` / `source_name` / `dim_invoice`·`dim_tax` / `cost_fen` / `skip_reason` 列。**未做 legacy 回填**：新表只承载改造后的请求，后台下钻对历史请求返回空列表 |
| 后台下钻路由 `/audits/{requestId}/sources` | 实为 `/audits/{requestId}/calls` |

§4.1 的判定表与 D1/D2 结论（有源查得即 `001` 且计费，`002` 收窄为「未取得数据且部分源异常」）
均按原设计落地，未变。

## 1. 目标

1. **计费口径**：聚合路由只要有**任意一个源查得数据**，就算本次查询成功，对下游计费。
2. **按源对账**：记录本次请求里**每一个源**各自的调用结果与上游标识（订单号 / 请求号），
   供向各家上游分别对账。
3. **结构统一**：单源路由与多源路由共用同一套记录结构，某条路由将来从单源变多源时
   不需要再迁移表或改后台。

## 2. 现状与缺陷

### 2.1 五个源的上游标识被丢掉四个（核心缺陷）

聚合器把各子源的 uid/logid 归并为**一对**值，策略是"第一个非空胜出"：

```go
// internal/infrastructure/upstream/aggregate.go
for _, r := range results {
    sections[r.label] = r.section
    if uid == "" && r.uid != "" {
        uid = r.uid
    }
    if logid == "" && r.logid != "" {
        logid = r.logid
    }
    ...
}
```

一次 swfp 查询会产生 5 个上游订单号与 5 个请求号，落库只留 1 个。
`billing_ledger` 与 `audit_log` 都是**一次下游请求一行、只有一对上游标识列**的形状，
这是把 1:N 关系硬塞进 1:1，**物理上装不下目标 2**。必须引入子表。

### 2.2 `billing_ledger` 的四个上游列从未被写入

`Append` 的 INSERT 语句里带了 `upstream_code / busi_code / upstream_uid / upstream_logid`，
但 `quota.Begin` 构造 `model.Ledger` 时只填 `AppKey/Version/TradeNo/Reqid/RequestID/State`，
结算时的 `UpdateState` 又只更新 `state / counted_service / settled_at`。
**这四列在生产库里恒为空**，当前对账只能依赖 `audit_log`。本次一并修掉。

### 2.3 `002` 混淆了两种语义

`aggregate.go` 现在只要 `errCnt > 0` 就归 `002`，把两种完全不同的情况合并了：

| 实际情况 | 现在的码 | 现在是否计费 |
|---|---|---|
| (a) 有源查得 + 有源失败 | `002` | 否 ← **目标 1 要改的就是这个** |
| (b) 无源查得（其余查无）+ 有源失败 | `002` | 否 |

因此**不能**简单地把 `"002"` 加进 `billing.returnedCodes`——那会让 (b) 也计费。

### 2.4 现有表职责（说明为什么最终是三张表而不是两张）

评审意见提出"裁成两张表：一张记我方操作，映射到上游"。方向正确，但**我方侧已经有两张主表**，
且是有意分开的：

| 表 | 写入时机 | 职责 | 能否合并 |
|---|---|---|---|
| `billing_ledger` | 调上游**之前**同步写 PENDING | 崩溃安全锚点、幂等键 `(app_key, version, reqid)`、计费状态机 | 不建议 |
| `audit_log` | 响应**之后**异步追加 | 操作日志：脱敏入参、耗时、client_ip、错误详情 | 不建议 |

合并会把"事后才知道"的字段（耗时、结果、错误）压进同步热路径，最终仍需一次 UPDATE，
且会破坏 PENDING 台账"响应前必落库"的崩溃安全语义。**本方案保持两张主表不动，新增一张子表。**

最终形态：`billing_ledger`（计费主表） + `audit_log`（操作日志） + `upstream_call`（**每源一行**，新增）。

## 3. 已确认的决策

| # | 决策 | 结论 |
|---|---|---|
| D1 | 「无源查得（其余全查无）+ 有源失败」是否计费 | **不计费**。只有"至少一个源查得到数据"才计费 |
| D2 | 下游业务码 | **有源查得就返 `001`**；`002` 收窄为"未拿到数据且部分源异常"，仍不计费 |
| D3 | 单源路由是否也写子表 | **写**。单源写 1 行，结构与多源完全一致 |
| D4 | 旧数据 | **回填** `source_label='legacy'` 一行，后台只保留一套查询路径 |

## 4. 计费与业务码口径变更

### 4.1 新判定表

| 子源结果组合 | `body.code` | 计费(`serviceUsed`) | `totalCalls` | 台账 |
|---|---|---|---|---|
| ≥1 源查得（**无论是否有源失败**） | `001` | **是** | +1 | BILLED |
| 无源查得 + ≥1 源失败 | `002` | 否 | +1 | BILLED |
| 全部查无（无失败） | `999` | 否 | +1 | BILLED |
| 全部失败 | — → `505062` | 否 | 不加 | PENDING → 复查/对账 |

### 4.2 实现成本：只是交换两个 switch 分支的顺序

`aggregate.go` 现在的判定是（"全部失败"已在前面提前返回）：

```go
switch {
case errCnt > 0:   // ← 先判失败
    return ... "002" ...
case okCnt > 0:
    return ... "001" ...
default:
    return ... "999" ...
}
```

改成先判"有没有查得"即可：

```go
switch {
case okCnt > 0:    // ← 只要有源查得就是成功，哪怕别的源挂了
    return ... "001" ...
case errCnt > 0:   // 无查得 + 有失败
    return ... "002" ...
default:
    return ... "999" ...
}
```

**`internal/domain/billing/billing.go` 完全不用改**：`returnedCodes` 里本来就只有 `001`，
`002` 本来就在 `resolvedCodes`（确定结论、BILLED、不计费）。新口径与现有判定表天然吻合。

### 4.3 对外契约影响

`README.md` 第 9 行与第 174 行现在写的是「聚合特有业务码 `002` = 部分数据源成功（不计费）」，
`docs/API_接口文档与使用手册_swfp.*` 同步。按 D2，`002` 的含义改为：

> `002` = **未取得数据，且部分数据源异常**（不计费）。
> 部分源异常但已取得数据的情况归 `001`（计费），哪些源异常见 `result.range` 的 `sourceStatus`。

这是**放宽**而非收紧：原本判为 002 不计费的 (a) 类请求现在返回 001 并计费。
需要商务侧知会客户，并注意**历史统计口径不可直接与新口径比较**。

### 4.4 契约层无需改动

`swfpcontract.go` 对 `001` 与 `002` 走同一条映射路径，且已经把每个源的
`sec.Status` 写进 `sourceStatus`，`001` 的 range 里出现 `error` 段是既有能力，无需修改。

## 5. 表结构改造

### 5.1 新增 `upstream_call`（每源一行）

```sql
CREATE TABLE upstream_call (
    id             BIGSERIAL    PRIMARY KEY,
    -- 关联键：与 billing_ledger 的唯一键同构，可直接 join
    app_key        VARCHAR(64)  NOT NULL,
    version        VARCHAR(16)  NOT NULL,
    reqid          VARCHAR(32)  NOT NULL,
    request_id     VARCHAR(64)  NOT NULL,            -- = head.logId，用于 join audit_log
    -- 子源身份
    source_label   VARCHAR(32)  NOT NULL,            -- invoice1/tax1/sales；单源路由填上游 kind
    source_alias   VARCHAR(16)  NOT NULL DEFAULT '', -- 对下游脱敏编号 源1..源5；单源留空
    provider       VARCHAR(32)  NOT NULL DEFAULT '', -- 上游 kind：entcredit/salesdata/gama…
    -- 该源本次的结论与上游标识（对账凭据）
    status         VARCHAR(8)   NOT NULL,            -- ok | empty | error
    upstream_code  VARCHAR(16)  NOT NULL DEFAULT '',
    upstream_msg   VARCHAR(256) NOT NULL DEFAULT '',
    upstream_uid   VARCHAR(64)  NOT NULL DEFAULT '', -- 该源的上游订单号 / tradeNo
    upstream_logid VARCHAR(64)  NOT NULL DEFAULT '', -- 该源的上游请求号 / requestId
    billable       BOOLEAN      NOT NULL DEFAULT FALSE, -- 该源是否构成本次计费依据(status=ok)
    latency_ms     BIGINT,
    created_at     TIMESTAMPTZ  NOT NULL DEFAULT now(),
    CONSTRAINT uq_upstream_call UNIQUE (app_key, version, reqid, source_label)
);

CREATE INDEX idx_upcall_request_id ON upstream_call (request_id);
CREATE INDEX idx_upcall_ledger_key ON upstream_call (app_key, version, reqid);
CREATE INDEX idx_upcall_uid        ON upstream_call (upstream_uid);
CREATE INDEX idx_upcall_logid      ON upstream_call (upstream_logid);
CREATE INDEX idx_upcall_recon      ON upstream_call (version, source_label, created_at);
```

设计要点：

- **关联键用业务键 `(app_key, version, reqid)`，不用 `ledger_id` 外键**。它与
  `billing_ledger` 的唯一约束完全同构，join 天然对齐，也不依赖台账自增 id 在内存中传递；
  再冗余一列 `request_id` 用于 join `audit_log` 和后台按 requestId 下钻。
- **唯一约束带 `source_label`**，因此重试/重放是幂等的（`ON CONFLICT DO NOTHING`）。
- **字符列一律 `NOT NULL DEFAULT ''`**，避免 Go 侧 `NULL` 与 `''` 的二义（现有两张表是
  可空列，新表不再沿用这个包袱）。
- `billable` 冗余存该源是否为计费依据，使"这笔钱是哪个源挣来的"可以单表查询，
  不必回头 join 台账再推导。

### 5.2 `billing_ledger`：补写既有空列 + 增加三个汇总列

不新增表，只补 §2.2 的历史欠账，并加三个便于对账速查的计数列：

```sql
ALTER TABLE billing_ledger ADD COLUMN IF NOT EXISTS source_total SMALLINT NOT NULL DEFAULT 0;
ALTER TABLE billing_ledger ADD COLUMN IF NOT EXISTS source_ok    SMALLINT NOT NULL DEFAULT 0;
ALTER TABLE billing_ledger ADD COLUMN IF NOT EXISTS source_err   SMALLINT NOT NULL DEFAULT 0;
```

并在结算时真正写入 `upstream_code / busi_code / upstream_uid / upstream_logid`
（值取"代表源"：优先第一个 `status=ok` 的源，其次第一个非空标识的源）。

### 5.3 `audit_log`：不动

**保留** `upstream_uid` / `upstream_logid` 两列并继续写入代表值。
现有后台"操作记录"页面零改动即可继续工作；新的"按源展开"能力由 `upstream_call` 提供。
待新页面稳定运行一段时间后，再单独评估是否废弃这两列。

## 7. 数据迁移 `migrations/0005_upstream_call.sql`

按 D4 回填一行 `legacy`，使后台无需写"查不到子表就回退读旧列"的分支：

```sql
INSERT INTO upstream_call
    (app_key, version, reqid, request_id, source_label, status,
     upstream_code, upstream_uid, upstream_logid, billable, latency_ms, created_at)
SELECT a.app_key, a.version, COALESCE(a.reqid,''), a.request_id, 'legacy',
       CASE WHEN a.found_data      THEN 'ok'
            WHEN a.called_upstream THEN 'empty'
            ELSE 'error' END,
       COALESCE(a.upstream_code,''), COALESCE(a.upstream_uid,''), COALESCE(a.upstream_logid,''),
       a.billed, a.latency_ms, a.created_at
FROM audit_log a
WHERE COALESCE(a.upstream_uid,'') <> '' OR COALESCE(a.upstream_logid,'') <> ''
ON CONFLICT (app_key, version, reqid, source_label) DO NOTHING;
```

注意事项：

- 迁移在 relay 启动时自动执行。若某个域库的 `audit_log` 体量很大，这条回填会拖长启动时间；
  **建议先在生产各域库上 `SELECT count(*)` 估算**，超过百万级就把回填拆成独立脚本分批跑，
  迁移文件里只留建表与 ALTER。
- 回填出来的行 `source_label='legacy'`、`provider=''`，与新数据天然可区分。
- 历史 `reqid` 可能为空，`COALESCE` 兜底为 `''`；配合 `ON CONFLICT DO NOTHING`
  可安全重复执行。

## 10. 待定 / 超出本次范围

- **聚合路由的逐源复查**：`Aggregator.Requery` 多源时恒返回 `Reachable=false`，
  PENDING 台账只能靠人工对账。有了 `upstream_call` 之后就具备了逐源复查的数据基础
  （知道每个源各自的 uid），但逐源 Requery 本身另案处理。
- **`trade_no` 语义**：下游至今未传 `tradeNo`，`billing_ledger.trade_no` / `audit_log.trade_no`
  恒为空。本方案中"每个源的 tradeNo"落在 `upstream_call.upstream_uid`。
  若将来下游开始传自己的 `tradeNo`，走主表的 `trade_no` 列，两者不要混用。
- **幂等重放的完整回放**：`replay` 目前不缓存完整 range。不在本次范围内。
